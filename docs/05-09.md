## Part 2：ACL —— settings.json 规则评估

### 2.1 想做什么

让用户能在 `.agents/settings.json` 写规则：

```json
{
  "rules": [
    { "tool": "shell", "pattern": "rm -rf *", "behavior": "deny" },
    { "tool": "write", "pattern": ".env*", "behavior": "ask" },
    { "tool": "read", "pattern": "*.md", "behavior": "allow" },
    { "tool": "*", "behavior": "ask" }
  ]
}
```

每条规则三件事：哪个 tool / 什么 content（glob）/ 什么 behavior（allow/deny/ask）。

### 2.2 层级查找

参考 git 的 `.gitignore` 多层查找：

```
cwd/.agents/settings.json
cwd/../.agents/settings.json
... 向上直到 git root 或 $HOME
~/.local-agent/settings.json   ← 用户全局兜底
```

closer-to-cwd 覆盖远的（`mergeSettings()`）。

### 2.3 评估器决策

```ts
function evaluatePermission(toolName, ruleContent, rules):
  // 第一遍：全表扫 deny（deny 最强）
  for rule in rules:
    if rule.behavior === "deny" && matches(rule, toolName, ruleContent):
      return "deny"
  // 第二遍：第一条 allow / ask 胜
  for rule in rules:
    if matches(rule, toolName, ruleContent):
      return rule.behavior   // allow or ask
  return null   // 没规则匹配，调用方走默认逻辑
```

`*` 在 tool 字段表示"所有 ACL-aware 工具"（即 `approvedTool` 包装的）。

### 2.4 接进 approvedTool

每个 ACL 工具传 `name` + `getRuleContent` + `getCwd`：

```ts
shellTool = approvedTool({
  name: "shell",
  getRuleContent: ({command}) => command,
  getCwd: (ctx) => getWorkspaceToolContext(ctx).sandbox.workingDirectory,
  needsApproval: (...) => shellNeedsApproval(...),  // 兜底
  execute: async ...
})
```

`approvedTool` 的 `needsApproval` 自动按决策树跑：

```
ACL 评估 → deny / allow / ask / null
  deny → execute 阶段返 toolErr（不抛错，避免 orphan tool call）
  allow → 跳审批
  ask → 强制弹审批
  null → 落回 user-provided needsApproval
```

execute 阶段也独立再 check 一次 ACL deny（防 time-of-check-vs-time-of-use 漂移）。

## Part 3：PermissionMode —— 会话级三档

claude-code 的设计移植：每个 chat session 有个"权限模式"字段：

| Mode | 行为 |
|---|---|
| `default` | 现有行为：每个工具按 needsApproval 决定 |
| `acceptEdits` | write/edit 自动过审批，shell 仍按原逻辑 |
| `bypassPermissions` | 全部自动过；**受 settings 双闸控制** |

### 3.1 双闸 bypass（学 claude-code）

直接切到 bypass 还不够 —— settings.json 必须显式开：

```json
{
  "allowBypassMode": true,            // 1. 必须打开才允许
  "disableBypassPermissionsMode": "disable"  // 2. 设了"disable"永久禁用，连 1 都覆盖不掉
}
```

第 2 个是 kill switch，对组织 IT 管理员场景：用户写 `allowBypassMode: true` 没用，组织管理员在
全局 `~/.local-agent/settings.json` 写 disable 就一票否决。

### 3.2 决策树（最终形态）

```
needsApproval(input, ctx):
  decision = ACL.evaluate(toolName, ruleContent, settings.rules)
  if decision == deny  → return false  (execute 返 toolErr)
  if decision == allow → return false
  if decision == ask   → return true
  if decision == null:
    if isSubagentCtx(ctx) → return false  (子 agent 无 UI 跳审批)
    if mode == bypass && isBypassModeAllowed(settings) → return false
    if mode == acceptEdits && tool ∈ {write,edit} → return false
    fall through → user-provided needsApproval
```

**ACL deny 永远第一**。即使 bypass + 双闸全开，settings.json 里 `tool: "*", behavior: "deny"`
还是会拦下来。这是 settings.json"组织级护栏"的语义保证。

### 3.3 UI 切换

`SessionHeader` 加循环 chip：default(灰) → acceptEdits(绿) → bypass(红) → 回 default。
PATCH `/api/sessions/[id]` 带 `permissionMode` 落库（schema v2 加列）。

## Part 4：Plan mode（codex 风格）

### 4.1 跟之前 `/api/plan` 的区别

| | 老 `/api/plan` | 新 plan mode |
|---|---|---|
| 入口 | 独立路由 + PlanCard | 主 chat 内切模式 |
| 性质 | 一次性 streamObject 出 JSON | 持续多轮的对话状态 |
| continuity | 断 —— plan 阶段对话不进主历史 | 连续 —— plan 阶段就是主对话的一部分 |
| 工具 | 不接工具 | read/grep 能用，write/edit/update_plan 被屏蔽 |

老 `/api/plan` 保留没动；新 plan mode 是补充，覆盖"探索式 plan"那种需要边读代码边讨论的场景。

### 4.2 移植 codex `plan.md`

[`tmp/codex-latest/codex-rs/collaboration-mode-templates/templates/plan.md`](../tmp/codex-latest/codex-rs/collaboration-mode-templates/templates/plan.md)
原文 128 行**几乎原样**搬到 `app/api/chat/plan-mode-prompt.ts`。只改两处：

1. `request_user_input` → `ask_user_question` / `ask_choice`（codex 工具名 → 我们的）
2. 末尾追加"用户用 UI plan-mode toggle 退出"

保留：三阶段（ground / intent / implementation chat）、`<proposed_plan>` XML 块约定、
non-mutating 严格定义。**不重新发明 prompt**，因为 codex 那 128 行是真的踩出来的。

### 4.3 toolset 过滤

主 chat workflow `app/workflows/chat.ts` 在构造 toolset 时按 plan + memoryEnabled
做集合过滤：

```ts
const filterKeys = new Set<string>();
if (options.planMode) {
  filterKeys.add("update_plan");
  filterKeys.add("write");
  filterKeys.add("edit");
}
if (!memoryEnabled) {
  filterKeys.add("memory_write");
}
const tools = filter(baseTools, key => !filterKeys.has(key));
```

shell 不过滤 —— plan.md prompt 里软约束"non-mutating commands only"。

### 4.4 chip + 状态点 step counter

plan mode 默认 `update_plan` 被屏蔽，没了 plan checkbox 进度信号。chat header 状态点
旁加紫色 "探索 N 次" 计数（数最新 assistant message 里的 tool-* part），让用户
看到 agent 还在干活，不是卡死。

## Part 5：update_plan / spawn_agent 重命名 + 升级

### 5.1 todo_write → update_plan + schema 简化

老 schema（open-agents 完整版）：
```ts
{ goal, steps: [{ id, title, status, note? }] }
```

新 schema（codex 风格）：
```ts
{ explanation?, plan: [{ step, status }] }
```

去掉 `id`/`goal`/`note`：

- LLM 偶尔忘 id 跨快照稳定（实测 gpt-4 偶发，小模型常发）
- 我们的 UI 没用上 id（render key 用 index 就够），是**纯成本零收益**
- codex 也是简化版

UI 兼容历史：MessageBubble 双匹配 `update_plan || todo_write`，老消息照样渲染。

### 5.2 task → spawn_agent + 全能子 agent

`task` 是只读 explorer，搬到 `spawn_agent` 给完整工具集（read/write/shell）。
schema 跟 codex 对齐：

```ts
{ message, fork_context? }
```

`fork_context` v1 没真实现（没真正传父对话历史进去），父 agent 必须把所有相关
context 写进 message 字段。fork_context: true 收下不抛错但 ignore，等真有需求
再补。

子 agent 跑在 `runSubAgent()` 里：

- toolset：read/glob/grep/write/edit/shell（**没** interactive ask_*，**有**
  spawn_agent 自身 ← 允许递归）
- ctx 注入 `__subagent: true` flag → approvedTool needsApproval 看到这个直接跳
  审批（subagent 没 UI 弹卡）。**ACL deny 仍然第一时间生效**，安全护栏在
- ctx 注入 `__subagentDepth: N` → spawn_agent execute 读这个判断递归是否触顶

## Part 6：spawn_agent v3 —— 递归 + 深度 + UX

### 6.1 递归

子 agent 的 `subAgentToolset` 包含 `spawn_agent` 自身（lazy import 破循环依赖：
`spawn-agent.ts` ← runSubAgent ← `sub-agent.ts` ← spawnAgentTool）。子 agent
能再 spawn 孙 agent。

### 6.2 深度限制（学 codex `agent_max_depth`）

`env.subAgentMaxDepth` 默认 2（主→子→孙）：

```ts
spawn_agent.execute(input, ctx):
  parentDepth = ctx?.__subagentDepth ?? 0    // 主 agent = 0
  childDepth  = parentDepth + 1
  if childDepth > env.subAgentMaxDepth:
    return toolErr("depth limit reached (...)") 
```

错误信息明确 `Current depth=2; refusing to spawn at depth=3`，让父 agent 自己
决定怎么应对（自己做完 / 拆任务 / 上报）。

### 6.3 UX 三件

- **运行中卡片**（`SpawnAgentRunningCard.tsx`）：紫色 + elapsed timer +
  task 摘要 + 阶梯式提示语（< 10s "在干 / < 60s "通常 30-90s 完成" / > 180s
  "跑得久了，要不要停"）。解决"看着像卡死"
- **完成后输出**：`toolBreakdown` 字段统计 `read×5 / grep×3 / write×2`，
  output card 渲染成 chip 列表 + depth 标签
- **header 徽章**：紫色 "● N subagents" 跳动小点（数 messages 里
  state ∈ {input-streaming, input-available} 的 spawn_agent tool part），
  让用户知道有几个 subagent 还在跑

## Part 7：UX 卡片体系（proposed_plan / implementation_summary）

### 7.1 codex 的 XML 块模式

codex 在最终回复里嵌特殊 XML 块表达"这是结构化的输出"：

```
<proposed_plan>
plan content
</proposed_plan>
```

UI 端用 stream parser 把它从 visible text 里**剥离**渲染成专属卡。

### 7.2 我们移植的两个块

| 块 | 何时出 | 卡片操作 |
|---|---|---|
| `<proposed_plan>` | plan mode 收尾 | 「采用此方案」（关 plan + 自动发实施指令）/「复制」 |
| `<implementation_summary>` | default mode 多文件改动收尾 | 「创建 commit」（agent 跑 git commit）/「复制」 |

### 7.3 通用 splitter

`app/_components/assistant-blocks.ts` 的 `splitOnBlocks(text)` 用一个组合
正则识别两种块：

```ts
const regex = /<(proposed_plan|implementation_summary)>([\s\S]*?)<\/\1>/g
```

返回 `[text, plan, text, summary, ...]` 段数组。MessageBubble 按段渲染，块外
走 markdown，块内走对应 Card。

未来要加新块（比如 `<oai-mem-citation>`），加进 BlockKind 类型 + 注册个新 Card 即可。

## Part 8：Memory pipeline（A1+A2+A3+A4）

### 8.1 总图

```
~/.local-agent/
├── settings.json                          ← memoryEnabled 等开关
└── memory/
    ├── MEMORY.md                          ← Phase 2 整合的索引（A1 注入）
    ├── raw_memories.md                    ← Phase 1 抽出的原始事实
    ├── <topic-slug>.md                    ← A4 主动写的主题文件
    └── rollout_summaries/
        └── <thread-id>-<slug>.md          ← Phase 1 每个 session 一份总结
```

### 8.2 数据流

```
用户发消息 → POST /api/chat
  ├─ fire-and-forget Phase 1（针对 thread 的 last_offset 之后的 jsonl）
  └─ 主 workflow → 当前 turn 流式回复
       ↓
（用户拿到回复）
       ↓
Phase 1 后台跑完
  raw_memories.md 追加段落
  rollout_summaries/<id>-<slug>.md 写好
  memory_extraction_state.last_offset 推进
       ↓ if wroteRawMemory
Phase 2 fire-and-forget
  算 raw_memories.md SHA256
  hash 跟上次一致 → skip（核心省钱机制）
  hash 变了 → LLM 调用整合 → 重写 MEMORY.md
       ↓
下次用户发消息 → A1 注入新 MEMORY.md → agent 看到
```

### 8.3 A1 注入

`lib/chat-agent/builder.ts` 在 `prepareCall` 里读 `settings.memoryEnabled` →
启用就调 `loadGlobalMemory()` 读 MEMORY.md（截断到 8000 字符）→ 通过
`prompt-layers.ts` 的新 `globalMemory` layer 注入，位于 envContext 之后 /
userInstructions 之前。

### 8.4 A2 Phase 1 抽取

`lib/memory/extractor.ts` 主流程：

1. memoryEnabled gate
2. retry cap gate（3 次连失败摆烂）
3. 读 thread + jsonl 增量
4. 提前检查"有 message 行吗"（只有 session_meta 直接推进 offset，**不调 LLM**）
5. 渲染 transcript（user > tool > assistant 优先顺序）
6. `generateObject` 调 LLM 拿 `{rollout_summary, rollout_slug, raw_memory}`
7. 写 raw_memories.md（追加） + rollout_summaries/<id>-<slug>.md
8. 推进 last_offset

prompt 在 `extractor-prompt.ts`，移植 codex `stage_one_system.md` 570 行精简到 200 行。
保留：no-op gate（没东西可记空返回）+ 4 类（user/feedback/project/reference）+ 安全规则
+ JSON schema。

### 8.5 A3 Phase 2 整合

`lib/memory/consolidator.ts`：

1. memoryEnabled gate
2. retry cap gate
3. 读 raw_memories.md 算 SHA256
4. **跟上次的 lastRawHash 对比 —— 一样就跳过 LLM 调用**（hash skip）
5. 读现有 MEMORY.md + 最近 10 个 rollout_summaries（按 mtime 倒排，每个截 500 字符）
6. LLM 调用，prompt 在 `consolidator-prompt.ts`（移植 codex consolidation.md
   300 行精简到 150 行）
7. 写新 MEMORY.md 覆盖
8. 推进 lastRawHash

整合后的 MEMORY.md 格式：

```md
# Memory index

_Last consolidated: 2026-05-09_

## Global (all projects)
- [user] Senior Go engineer learning Next.js 16
- [feedback] Don't auto-create test files. WHY: ...

## Project: /Users/apple/Desktop/project/CLIProxyAPI
- [project] Migrating auth/* to JWT, deadline 2026-06
```

按 scope 分组（global / per-workspace）。每条 ≤ 200 字符。

### 8.6 A4 主动写

agent 用 `memory_write` 工具：

```ts
{ topic, type, content, oneLineSummary }
```

- 写 `<topic>.md`（带 frontmatter）
- 同步追加 / 更新 MEMORY.md 索引一行
- ACL pattern 匹配 topic slug
- **不进 subAgentToolset**（子 agent 不该写用户全局 memory）

### 8.7 项目级开关

`.agents/settings.json` 写 `"memoryEnabled": false` → 整套（A1+A2+A3+A4）一刀切。

实现两端配合：

- A1 loader：disabled 直接返 null 不读文件
- A2/A3 触发处：disabled 立即 return 不调 LLM
- A4 工具：通过 toolset 过滤掉 `memory_write`，agent 看不到

### 8.8 模型档位

`MEMORY_EXTRACTOR_MODEL` env，没配 fallback 主模型。Phase 2 也用同一个 env
（暂时单档，对齐 codex 的"Phase 1 mini + Phase 2 full"两档将来加
`MEMORY_CONSOLIDATOR_MODEL` 即可）。

## Part 9：现在的安全栈全貌

```
┌─────────────────────────────────────────────────────┐
│  agent 想调任意 mutating 工具                        │
└──────────────────────┬──────────────────────────────┘
                       ↓
            ┌──────────────────────┐
            │ ACL evaluator        │  ← settings.json rules
            └──────────────────────┘
            deny → toolErr
            allow → 跳审批
            ask → 弹审批
            null ↓
            ┌──────────────────────┐
            │ subagent ctx?        │  ← __subagent flag
            └──────────────────────┘
            yes → 跳审批
            no ↓
            ┌──────────────────────┐
            │ PermissionMode       │  ← session level
            └──────────────────────┘
            bypass + 双闸通过 → 跳审批
            acceptEdits + write/edit → 跳审批
            其它 ↓
            ┌──────────────────────┐
            │ tool's needsApproval │  ← 工具自己的默认
            └──────────────────────┘
            true → 弹审批
            false → 直接执行
```

七层防御从严到松：

| # | 防线 | 触发条件 |
|---|---|---|
| 1 | `memoryEnabled=false` 一刀切 | settings 字段 |
| 2 | `disableBypassPermissionsMode: "disable"` 永久禁 bypass | settings 字段 |
| 3 | ACL deny 规则 | settings.rules |
| 4 | ACL ask 规则 | settings.rules |
| 5 | 工具自身 needsApproval（如 `.env*` 弹审批） | tool 代码 |
| 6 | shell 命令安全黑名单（rm -rf / 等） | shell-approval.ts |
| 7 | **Schema zod regex** | 路径穿越 / 恶意 slug 在最早 reject |

## Part 10：踩过的坑

### 10.1 ACL deny 抛错 → orphan tool call

**症状**：第一次实现 ACL deny 直接在 `needsApproval` 抛 Error。结果 chat 报
"No tool output found for function call call_xxx"。

**原因**：AI SDK 在 `needsApproval` 抛错时 tool call 卡在"没 output"状态。下次
请求 gateway 看到 tool call 没配对 result，整次请求被拒。

**修法**：deny → `needsApproval` 返 false（不弹审批），`execute` 阶段返
`toolErr({error: "denied by ACL..."})`。tool call 拿到合法 output，agent 看到
错误信息能正常调整方向。

### 10.2 useChat transport 闭包陈旧

**症状**：UI 上 `PLAN: ON` chip 显示已切，但请求 body 里 `planMode: false`。

**原因**：`new DefaultChatTransport({ body: () => ... })` 闭包在 mount 时锁
住，后续 transport 实例换了 useChat 也不重新读。`activeSession.planMode` 改
变时虽然 useMemo 重建 transport，但 useChat 拿到的还是 mount 那一刻的 body 闭包。

**修法**：transport 只创建一次（deps=[]），body() 通过 sessionRef 读最新值。
`sessionRef.current = activeSession` 在每次 render 时同步更新，body() 调用时
现读 ref，永远拿当前值。

### 10.3 mergeSettings 漏字段

**症状**：用户在 `~/.local-agent/settings.json` 写 `memoryEnabled: false`，
agent 还在读 memory。

**原因**：加 schema 时只动了 schema 定义和消费层，**漏改了 mergeSettings**。
合并时 `memoryEnabled` 字段被丢，最终结果是 undefined → `isMemoryEnabled` 默认
true → memory 仍启用。

**修法**：mergeSettings 加 `memoryEnabled: override.memoryEnabled ?? base.memoryEnabled`。

**教训**：往 zod schema 加 optional 字段时，**必须 grep 一遍 mergeSettings 确认所有
合并路径都覆盖到**。这种 bug ESLint / TS 都抓不到（schema 是 zod，optional 字段
不出现就是合法）。

### 10.4 ripgrep 二进制 ENOENT

**症状**：`searchWorkspace` 每次 grep 都 fallback 到 Node 实现（慢 5-10x）。
日志：`/bin/sh: /ROOT/node_modules/@vscode/ripgrep/bin/rg: No such file or directory`。

**原因**：Turbopack 把 `rgPath` 路径 bundle 时改写成 `/ROOT/...`（占位符），
runtime 找不到二进制。

**修法**：`next.config.ts` 把 `@vscode/ripgrep` 加进 `serverExternalPackages`，
让 runtime 才计算真路径。

### 10.5 AI_NoOutputGeneratedError 干挂 workflow

**症状**：agent 在 plan 模式或者本地 LLM 偶发返回空时，整个 workflow FatalError
退出。

**原因**：`smoothStream` 在 flush 阶段如果 0 chunk 处理过会抛
`AI_NoOutputGeneratedError`。我们没 catch，workflow 当 fatal 处理。

**修法**：`isNoOutputError()` helper + workflow step 里 catch，降级为
`finishReason: "stop"` 让 outer loop 自然 break + sendFinishChunk 收尾。
打 warn `[workflow/chat] step N produced no output; treating as stop`。

### 10.6 Phase 1 空 transcript 也调 LLM

**症状**：thread 刚建出来 jsonl 里只有 session_meta 行，extractor 还是发请求
被 401 拒。

**原因**：游标增量 > 0 直接调 LLM，没看新行里有没有真消息。

**修法**：extractor 在调 LLM 前提前扫一遍新行，只有 session_meta 类（没 message
类）就直接推进 offset 不调 LLM。

### 10.7 SessionHeader destructuring 漏字段

**症状**：v3 加完 activeSubagentCount，浏览器报
`activeSubagentCount is not defined`。

**原因**：TypeScript type signature 加了 `activeSubagentCount: number`，**但
`function ({...})` 那行的 destructuring 没加进去**。运行时是 undefined，渲染
访问就崩。

**修法**：加上去。

**教训**：手改组件 props 时**类型定义和 destructuring 必须成对改**。这个本来
TS 严格模式应该捕获，但 dev lint 没那么严。

## Part 11：后续可以做什么

### 11.1 短期可补

- **`/api/memory/consolidate` UI 入口**：现在只有 curl，加个 chat header 按钮
  "整合记忆" 触发 Phase 2
- **memory browse UI**：像 claude-code 的 `/memory` 命令，列 MEMORY.md 内容 +
  按钮删除某条
- **Phase 1/2 的 token 计费观测**：在 `[memory/phase1]` log 里加上 input/output
  token 数 + 当次 LLM 调用时长，方便估算每月 memory 烧钱
- **`fork_context: true` 真实现**：需要决定"传几轮历史 / token 预算"

### 11.2 中期值得做

- **memory_read 工具**（按需拉，不只是注入）：MEMORY.md 长大后，让 agent 显式
  按 topic 拉详细内容，prompt 注入 budget 不会爆
- **`<oai-mem-citation>` inline 引用**：codex 用这个块在 prose 里"引用某条 memory"
  来源。我们做完后 agent 回答可以"我从 memory 知道你偏好 pnpm"带 footnote
- **multi-model tier**：`MEMORY_CONSOLIDATOR_MODEL` 单独 env，让 Phase 2 用更强
  模型（codex 的 mini + full 双档真省钱）

### 11.3 长期 / codex 对齐

- **memory 用 git workspace diff 跳过 Phase 2**：codex 用 `~/.codex/memories/.git`
  做版本基线。我们目前用 SHA256 跳过，跟 codex 行为等价但更轻量；真要对齐
  / 跨工具互通，加 git baseline
- **subagent 真并发**：codex 默认 16 路并发跑 Phase 1。我们目前串行，长会话
  里抽取慢。要真并发得改 fire-and-forget 队列管理
- **claude-code `/agents` 风格 panel**：列出所有活跃子 agent + 单独 transcript
  看，就像 claude-code 的 Running tab

### 11.4 不打算做（选过）

- **MCP 暴露 memory 工具**：codex 用 MCP server 给多端复用。我们单 Next.js
  应用没这需求，in-process 更直接
- **Plan mode 完全替换 `/api/plan`**：streamObject 出 JSON Plan 是有差异化
  价值的（机器可读 plan），保留双轨

### 11.5 用户实测应当观察

- 多用几天看 raw_memories.md 真实抽出来的事实质量。Phase 1 prompt 太严会漏，
  太松会污染 MEMORY.md
- 看 MEMORY.md 长度。如果常常 > 8000 字符触截断，调
  `AGENT_MEMORY_MAX_CHARS` 或加 memory_read 工具按需拉

### 12.5 settings 层级查找顺序

```
cwd/.agents/settings.json                ← 最高优先级
cwd/../.agents/settings.json
... 直到 git root 或 $HOME
~/.local-agent/settings.json             ← 用户全局兜底
```

closer-wins，但 `disableBypassPermissionsMode: "disable"` 是 sticky（任意层级
设了就生效，下层覆盖不掉）。
